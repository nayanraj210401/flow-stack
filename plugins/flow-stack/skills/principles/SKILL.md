# Principles

Each principle is one short file in `references/`: the rule, why it holds, a bad and a good example, and a self-check. When a skill or hook cites `principle-<name>`, read `references/principle-<name>.md`, and only that file. In your reply, name the principle that changed a decision and what it changed.

| Principle | Apply when |
|---|---|
| [attack-the-premise](references/principle-attack-the-premise.md) | When fixes that share an assumption keep failing, stop, write the assumption down, and test it directly before another fix. Apply after 2 failed attempts at the same problem, and whenever the circuit breaker trips. |
| [build-the-lever](references/principle-build-the-lever.md) | For repeated or bulk work, write the tool that does it or proves it (a script, codemod, generator, or check) instead of working by hand. Apply when a change repeats more than about 5 times, when an analysis could be scripted, or when a check could be automated. |
| [checks-need-teeth](references/principle-checks-need-teeth.md) | A check that passes with and without your change proves nothing. Apply when writing or trusting a test, after a check passes, and when reviewing tests that mock heavily or only assert "no crash". |
| [design-it-twice](references/principle-design-it-twice.md) | Before committing to an approach, produce at least one genuinely different alternative plus the null option (delete, reuse, configure, don't build), and pick with evidence. Apply when choosing how to build something non-trivial, when you notice you have only one idea, and whenever you're defending an approach instead of evaluating it. |
| [encode-in-structure](references/principle-encode-in-structure.md) | When the same correction or instruction recurs, encode it as a lint rule, test, hook, type, or script default instead of more prose. Apply when writing a lesson, repeating an instruction, or seeing the same review comment twice. |
| [evidence-over-claims](references/principle-evidence-over-claims.md) | "Done" means output from running the real thing, not "it compiles", self-report, or "should work". Apply before saying done, fixed, works, or passes, and when reading a worker's report. |
| [fix-root-causes](references/principle-fix-root-causes.md) | Reproduce first, ask why until you reach the defect, and fix it there; no silencing guards or special cases. Apply when debugging, when a check fails, or when tempted to add a null check, try/catch, or input-specific branch to make an error go away. |
| [human-owns-irreversible](references/principle-human-owns-irreversible.md) | Proceed on reversible work and log it; stop and ask on irreversible, outward-facing, contract-changing, or taste decisions. Apply before any push, deploy, delete, migration, message, or spend, and whenever tempted to ask "should I…?". |
| [intent-before-code](references/principle-intent-before-code.md) | No code before the acceptance checks exist. Apply when starting any non-trivial change, when a request is vague, or when you notice you're building before knowing what done looks like. |
| [minimize-reader-load](references/principle-minimize-reader-load.md) | Judge code by the work a reader must do. Count layers to trace and state to hold, and cut both. Apply when shaping or reviewing code, deciding whether a new layer, wrapper, flag, or piece of state earns its place, and when a refactor needs a success measure. |
| [model-the-domain](references/principle-model-the-domain.md) | Encode the domain in a data structure (state machine, typed model, lookup table, discriminated union) instead of scattered conditionals and synced booleans. Apply when writing stateful logic, when a feature would add another branch to an if/else chain, or when two flags must stay in sync. |
| [parse-at-the-boundary](references/principle-parse-at-the-boundary.md) | Outside data is `unknown` until one function at the edge parses it into a domain type; inside, trust the type and shape it so wrong states can't be written. Apply when wiring input (CLI, HTTP, messages, files, LLM output), when the diff adds a cast, `!`, or suppression, and when a type needs a comment explaining which field combinations are valid. |
| [reader-first](references/principle-reader-first.md) | Write for a busy reader. Answer first, short, cited, and no restated context. Apply to every reply, report, commit message, PR description, and doc. |
| [red-before-green](references/principle-red-before-green.md) | See the check fail for the right reason before writing the code that makes it pass, then see it pass, then see it fail again without the change. Apply to every slice, bug fix, and feature where a check can run; skip only with a written reason (e.g. a behavior-preserving refactor, where the pin must stay green). |
| [redesign-not-bolt-on](references/principle-redesign-not-bolt-on.md) | Integrate a new requirement as if it had existed from day one; reshape the design rather than attaching a special case. Apply when adding a requirement to existing code, when a change needs a new flag threaded through layers, or when the natural diff is "one more if". |
| [smallest-verifiable-unit](references/principle-smallest-verifiable-unit.md) | Break work into small units that each end in a state a check can prove, ordered so the sequence proves itself. Apply when planning slices, stacking commits or PRs, or when a change grows past a few hundred lines. |
| [spend-cheap-save-expensive](references/principle-spend-cheap-save-expensive.md) | Three currencies (tokens, dollars, human attention) with very different prices; spend the cheap ones to save the expensive one. Apply when choosing between reading and delegating, asking and experimenting, long and short replies, or cheap and strong models. |
| [subtract-before-add](references/principle-subtract-before-add.md) | Delete > add. Look for removal, reuse, and configuration before writing new code; prefer the smallest diff; every net-added line must justify itself. Apply when starting any change, when tempted to add an abstraction, flag, file, or helper, and when reviewing a diff's size. |
| [untrusted-until-proven](references/principle-untrusted-until-proven.md) | A worker's (or your own earlier) output is a claim until evidence and review back it, and scaling agents is capped by the human's review capacity. Apply when delegating, merging worker results, or trusting a summary. |
